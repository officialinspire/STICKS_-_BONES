# Installable PWA and offline play

STICKS & BONES installs as a Progressive Web App from its GitHub Pages subpath,
for example `https://<owner>.github.io/STICKS_-_BONES/`. The same build works
under any subpath: the manifest, service worker and every cached URL are relative.

## What's in the build

| File | Purpose |
| --- | --- |
| `manifest.webmanifest` | `id`, `start_url` and `scope` are `./`, so they resolve to the subpath. Display is standalone. Four icons: 192 and 512 px for both "any" and "maskable". |
| `icons/*.png` | Generated by `npm run icons:build` from Cousin's approved portrait atlas (neutral frame, the game's own bust box), on a full-bleed teal field. `apple-touch-icon-180.png` is for iOS. |
| `sw.js` | The service worker, generated by the `sticks-pwa` Vite plugin from `src/pwa/sw.js` with this build's complete offline pack. |
| `build.json` | The build id, per-group byte totals and every shipped file with its bytes and SHA-256 (the same list the worker carries). |

### Maskable safe area

The maskable safe area is verified, not assumed. A maskable icon may be cropped
to any shape that contains the centred circle of radius 40% of the icon.

- The generator shrinks the art until every foreground pixel (alpha > 8) lies
  inside that circle.
- It records the measured worst radius in `src/assets/icons.json`. Measured:
  0.392–0.395 against a limit of 0.400.
- "Any" icons use the same art, up to 0.46.
- `npm run assets:verify` checks these things:
  - each icon's hash, size and recorded radius;
  - that the icons came from the current portrait sheet;
  - that every manifest icon is a verified generated file;
  - that `start_url` and `scope` are relative.

## Isolation from other INSPIRE apps on the same origin

GitHub Pages serves every repository of an owner from one origin, so other apps
share our CacheStorage, localStorage and service-worker registry.

- **Scope:** the worker is registered at `<app root>/sw.js` with scope = the app's
  directory, computed from the entry chunk's URL. It only answers requests under
  that scope; anything else goes to the network untouched.
- **Caches:** every cache this app creates is named `inspire:sticks-and-bones:*`.
  The worker and the page only ever open or delete caches with that prefix. A
  unit test covers look-alikes such as `inspire:sticks-and-bones-fan:v1` and
  `sticks-and-bones`.
- **No unregistering, no forced takeover:** nothing ever calls `unregister()`.
  The worker never calls `skipWaiting()` on its own.
- **Local data:** saves, settings and statistics use `sticks-and-bones.*` keys.
  "Erase" removes only those keys.
- `npm run pwa` serves a fake second app at `/other-app/` on the same origin,
  with its own worker, two namespaced caches, a generic cache and localStorage
  keys. It asserts that all of these survive first visit, offline play, repair,
  erase and update.

## Full offline storage: what is saved, and when

**Owner decision (this stage):** the owner authorized **full offline storage**. It replaces the earlier
policy (music and ambience only in an optional download, the intro video never cached). Every shipped
runtime file is now saved for offline play.

Every file the build ships is listed by the `sticks-pwa` plugin with its **exact byte size and SHA-256**
(`sw.js` → `GROUPS`, also in `dist/build.json`), computed from the files as written (`writeBundle`). The
build **fails** if a file would ship without an offline group, if a PNG other than the icons would ship, or
if two shipped files are byte-identical (a duplicate upload). `npm run build` (`scripts/check-dist.mjs`)
re-hashes `dist/` against `build.json`, checks that the pack holds the video, both background orientations,
cast sheets, ambience, result cues, SFX, the lazy Story chunk and fonts, and gates the pack size.

| Cache | Contents (measured, this build) | When |
| --- | --- | --- |
| `inspire:sticks-and-bones:shell:<build>` | HTML, every JS chunk (entry, AI worker, lazy Story and achievements chunks), CSS, fonts, manifest, **all five icons**, the two font licences — **18 files, 0.66 MB** | At install, all or nothing, each file checksum-verified |
| `inspire:sticks-and-bones:assets:v1` (core) | What Quick Play needs: both patio orientations, Cousin's portrait and slam, tile atlas, tabletop, effects, UI/table/pass sounds, **the two result cues** — **32 files, 1.78 MB** | At install, best effort: Quick Play is offline as soon as the worker is installed |
| `inspire:sticks-and-bones:story:v1` | Chapter backdrops (landscape + portrait), the four cast sheets, story sounds — **21 files, 2.86 MB** | The whole-game download (and, before that, cache-on-fetch as chapters are played) |
| `inspire:sticks-and-bones:media:v1` | The four songs/scene beds, the five ambience beds and **the INSPIRE intro video** — **10 files, 14.62 MB** | The whole-game download |
| `inspire:sticks-and-bones:meta:v1` | One entry: the build whose pack was last **verified** | Written only after verification |
| — | **Never shipped or cached:** PNG source sheets, the audio originals and other source masters (`assets/art/`, `assets/audio/originals/`), duplicate uploads (e.g. the second, identical "Round Win Stinger Alt" copy) | — |

**Whole game: 81 files, 19.92 MB (20,892,477 B)** per `dist/build.json`; `check-dist` gates it at 21,000 KB.
The retired `audio:v1` cache (optional audio from earlier releases) is **adopted, not re-downloaded**: a
file already held there under the same content-hashed path is re-hashed and copied; the cache is deleted
once this build is verified.

### The whole-game download

- **When:** after the essential startup — 1.5 s after the menu appears (or the player is returned to their
  story/match after an update) — and only while online. Startup never waits for it: initialization decodes
  only the fonts, one patio orientation, Cousin's portrait and the tile atlas (`docs/PERFORMANCE.md`), and
  `npm run pwa` checks that no Story or media file is requested before the menu.
- **Bounded:** 2 files at a time; a stalled transfer is aborted (≥ 20 KB/s or 30 s); each failed file is
  tried twice; at most 3 automatic runs per visit (15 s, 30 s apart), then it waits for **Retry**.
- **Data Saver** (`navigator.connection.saveData`): nothing starts by itself; the player taps **Download the
  full game (n MB)**. Chapters still save as they are played (current + prefetched next).
- **Storage estimate first:** if `navigator.storage.estimate()` says the remaining bytes (+10%) won't fit,
  nothing is downloaded and the player is told how much is needed and free. `navigator.storage.persist()` is
  requested **only on the player's own tap** (Download / Retry), never automatically, because some browsers
  show a permission prompt.
- **Resume:** files already stored with the right checksum are skipped, so an interrupted run (connection
  lost, transfer cut, the browser stopping the worker) continues where it stopped. The page treats 45 s
  without progress as "the worker was stopped" and resumes.
- **Verification:** after the downloads, the worker re-reads and **re-hashes every stored file**; a damaged
  copy is deleted and fetched once more. Only when all of them match does it write the `verified` marker.
  **"Full game ready offline" is shown only when that marker is for this build and every file is present**
  (the status check is cheap: presence + the stored checksum header; it never re-reads bodies).

### How files are stored and served

- **Stored:** only a complete `200` (never a `206`, a 404 page or an error), with exactly the listed bytes
  and SHA-256. Stored with `Content-Type` from the file extension (not the server's), `Content-Length`,
  `Accept-Ranges: bytes` and the checksum. A truncated or corrupt body is never stored.
- **Served cache-first** for every listed file, with the right MIME type. **Byte ranges:** one range →
  `206` with `Content-Range: bytes a-b/len`; a range starting past the end (or `bytes=-0`) → `416` with
  `Content-Range: bytes */len`; several ranges or a malformed header → the whole file, `200` (a server may
  ignore Range). `HEAD` is answered with headers only. Music and the intro video stream from the cache this
  way, so `<audio>`/`<video>` work offline.
- **Cache-on-fetch:** anything the game fetches before the download reaches it is kept, under the same
  checksum rule.
- **Old media until verified:** activation deletes only old shells (code for a build no page runs). Art,
  sounds, music and video entries of older builds **stay until this build's pack is verified**, then
  `prune()` removes everything this build doesn't list (and the retired caches). Offline, an image, sound,
  song or video this build hasn't saved yet is served from the previous build's copy of the same asset
  (same name stem, different content hash); code never falls back this way.

## What the game says (menu and Settings → Offline & storage)

| Line | Meaning |
| --- | --- |
| **✓ Full game ready offline (19.9 MB on this device).** | This build's whole pack is verified and present |
| **Saving the full game for offline play… 4.2 MB of 19.9 MB** / **Checking the saved files… 40 of 81** | The download / the verification pass (a progress bar in Settings; announced at most once per 10%) |
| **Quick Play is ready offline. The full game (n MB still to save) downloads while you're online.** | Shell + core saved; the rest not yet |
| **…The full-game download stopped at x of y MB. It continues by itself while you're online, or tap Retry.** | Interrupted (connection, cut transfer, worker stopped) |
| **…The rest of the game (n MB) saves when you're next online.** | Offline before the download finished |
| **…Data Saver is on, so the full game (n MB) waits for you to tap Download.** | Data Saver |
| **…Not enough storage for the full game: it needs n MB more, about m MB is free. Free up space, then Retry.** | By the estimate, or a quota error inside the worker |
| **…n files couldn't be downloaded from the server; everything else is saved. Retry later.** | 404s |
| **…n files arrived damaged and were discarded. Retry downloads them again.** | Checksum mismatch twice |
| **The browser cleared this game's offline files (storage ran low or site data was cleared).** / **n offline files were removed by the browser.** | Eviction: a verified copy existed (recorded in `sticks-and-bones.offline` v2), now missing; it downloads again while online |
| **…Your previous version's music and art stay usable until the new files are checked.** | After an update, before the new pack is verified |
| **This browser isn't storing offline files right now (private browsing or blocked site data). The game works online.** | Registration or storage refused |
| **Offline play isn't available in this browser — the game works online.** | No service worker |

Settings also shows the **storage line** — "This game keeps x of y MB on this device. About z MB free for
this site." plus whether the browser promised to keep the files (`persisted()`) or may clear them under
pressure — the **Download / Retry (n MB left)** button (hidden once verified), **Install the game** (shown
when the browser offers installation via `beforeinstallprompt`; otherwise a note says to use the browser's
Install / Add to Home Screen), and Repair. The free-space figure is the browser's estimate for the whole
origin (shared with other INSPIRE apps on GitHub Pages); "keeps" counts only this game's files.

The case file adds one line for the current scene: **"Saved for offline play."** or **"Needs a connection
until the full game has saved for offline play."** A scene whose art is missing offline still plays with the
drawn backdrop and name tags.

`sticks-and-bones.offline` is now version 2 (`{ verifiedBuild }`): the build last verified on this device,
used only to say honestly that the browser cleared the files. Version 1 (the retired story/audio choices)
migrates to "none recorded".

## Updates: "Update available" and how a waiting update is applied

1. A new deploy changes `sw.js` (the build id hashes every emitted file). The new worker installs next to the
   running one and **waits**; checks run on load, on returning to the tab and every 30 minutes.
2. **Update now** is offered on the menu, the case file, the story **scene bar**, and the pause sheet of any
   table (Quick Play or a story hand).
3. **Update now** first writes the stable state and checks the write succeeded:
   - a Quick Play match: the save from the engine state;
   - a story scene or hand: the case progress with the exact line, or the in-progress hand snapshot.

   **If the write is refused**, the player is told ("Your place couldn't be saved") and chooses **Not now —
   keep playing** (nothing reloads) or **Update anyway** (returns to the last saved point). It never claims
   to have saved.
4. Then the table is torn down (no AI move can land), the screen is replaced (no hand visible — checked at
   unload), and the worker takes over.
5. **After the reload, the start tap returns once** to where the player was: the same story line, the same
   hand (engine state identical), the case file, or the saved match. Two-player matches reopen behind the
   privacy cover. The return point is consumed before anything renders, so a second reload goes to the menu.

## Repair and erase (Settings → Offline & storage)

- **Repair offline files** is app-only: it deletes our stale caches (old shells, unknown names) and the
  verified marker, **re-hashes every stored file**, replaces any damaged copy, downloads what is missing and
  verifies again. **Both save slots (the Quick Play save and the Story case progress), settings, statistics
  and achievements are not touched**; other apps' caches and workers are not touched.
- **Erase saved game, settings & statistics…** (two taps) removes only `sticks-and-bones.*` keys; offline
  files are kept.

## Evidence (`npm run pwa`)

`npm run pwa` builds the app three times (A, B and C differ in `SB_BUILD_TAG`; C also renames one music file,
as a release that replaces a track would, with its pack re-signed) and serves them from `/STICKS_-_BONES/`
next to a fake second app with its own worker, caches and storage. The test server answers byte ranges like
GitHub Pages and can go down, cut transfers half-way, slow them, return 404 or send corrupted bytes.
`PWA_ONLY=3,9` runs a subset (sections 1, 2 and 6 always run). Measured results (Chromium, this stage):

1. **First visit (subpath):** manifest, icons, `start_url`/`scope`/`id` inside the subpath; installable (no
   installability errors); the Install button appears when the browser offers it and shows the prompt. No
   Story or media file is requested before the menu. The line goes "Saving the full game… 2.4 MB of 19.9 MB"
   → "Checking the saved files… 8 of 81" → "✓ Full game ready offline (19.9 MB on this device)." — never
   "ready" before the check. In the page, **every one of the 81 files** is read back and matches its bytes,
   SHA-256 and MIME type (19.93 MB = `build.json`); no source master or extra entry is cached. A copy planted
   in the retired `audio:v1` cache is adopted (not downloaded) and that cache is gone after verification.
2. **Cold offline launch:** the whole browser is closed and relaunched on the same profile, offline, with the
   server down. "Ready." → **the studio video plays from the cache** (1080×720) → menu still "Full game ready
   offline". Offline decode: a 178 s song, an ambience bed, the video, a result cue and a story sound. Byte
   ranges: 200 + `Accept-Ranges`, `bytes=100-1123` → 206, `bytes=-500` → 206, video `bytes=0-` → 206
   `video/mp4`, past the end → 416 `bytes */len`, multi-range → 200, `HEAD` → 200 without body. A hand vs the
   computer with atlas tiles; Chapters 3 and 6 over their own backdrops. **0 app requests** reached the
   network (only the browser's `sw.js` update checks).
3. **Interrupted install downloads** (tile atlas + table cut): "Quick Play works offline; 2 table files are
   still missing (the game draws them). The full-game download stopped at 19.5 MB of 19.9 MB…"; Retry button;
   nothing truncated stored; offline, a hand completes with vector faces. Back online it resumes by itself and
   fetches **only the 2 missing files** → ready.
4. **Quota:** by the estimate (1 MB free) → "needs 17.5 MB more, about 1.0 MB is free", nothing downloaded; a
   real quota error in the worker (4 MB quota) → the same honest message; a 40 KB quota (no shell) → "Not
   enough storage on this device…". An online hand completes in each.
5. **Update A → B mid-match**, two humans: no hand visible at unload; save identical; reopens covered; one
   shell cache (B's).
6. **Repair:** a stale cache of ours and a **silently corrupted** stored copy (same size and headers) →
   re-hashed, replaced → ready; localStorage byte-identical. **Erase:** only our keys; the pack kept.
7. **Data Saver:** nothing downloads by itself ("…waits for you to tap Download"); Chapter 1 and the
   prefetched Chapter 2 save as played; offline, Chapter 5 uses the drawn backdrop; **Download the full game
   (16.1 MB left)** → progress bar → ready → Chapter 5 offline over its art.
8. **Interrupted whole-game download:** (a) the browser stops the worker at 4.1 MB → detected (~50 s) → "stopped
   at 5.3 MB of 19.9 MB…" → resumes by itself, **none of the 53 saved files fetched again** → ready. (b) a
   song and a cast sheet cut mid-transfer → "Retry (2.9 MB left)", storage line "keeps 17.1 MB of 19.9 MB";
   Retry fetches **only those 2** → ready.
9. **Corrupted bytes** (right length, wrong content, twice) → "1 file arrived damaged and was discarded" —
   not stored; Retry → ready.
10. **Eviction:** all caches cleared → "The browser cleared this game's offline files…" → downloaded again →
    ready; the media cache removed → "10 offline files were removed by the browser." → ready.
11. **Update mid-case:** dialogue line and an in-progress hand restored once; a refused save is reported; an
    older build's art planted in the story cache is pruned once B's pack is verified.
12. **Upgrade retention (A → C):** C's new track 404s → "1 file couldn't be downloaded… Your previous
    version's music and art stay usable until the new files are checked."; **offline, C's track URL plays
    from A's retained copy** (200 `audio/mpeg`, identical SHA-256, Range → 206, `<audio>` canplaythrough);
    Retry → ready, and only then is the old copy pruned.
13. **Storage unavailable** (registration refused) → "This browser isn't storing offline files right now…";
    an online hand completes.

Throughout: the other app's worker, caches and storage are untouched; axe finds no serious violations on the
offline panel (ready and interrupted) or the pause sheet with the update banner.

## Known browser limitations

None of these have been tested on real devices; see `docs/QA.md`.

- **iOS / iPadOS Safari:**
  - No install prompt (no `beforeinstallprompt`): the Settings note tells players to use Share → Add to Home
    Screen.
  - A home-screen app has **its own storage**, separate from Safari's, so saves don't move between them.
  - Script-writable storage, including caches, may be **evicted after about 7 days without use** for sites
    that aren't installed. The game then says the browser cleared the files, and downloads them again online.
  - Total storage per origin is limited (historically ~1 GB on recent iOS, less on old versions); the 19.9 MB
    pack fits, but the estimate check reports honestly if it doesn't.
  - The 512-px maskable icon isn't used; `apple-touch-icon-180.png` is.
- **Firefox desktop:** service worker and offline play work, but Firefox doesn't offer to install sites as
  apps (no Install button appears). `persist()` shows a permission prompt in Firefox, which is why it is only
  called on the player's own tap.
- **Private browsing:** some modes disable service workers or storage. The status then says offline files
  aren't being stored, and the game still works online.
- **Storage is "best effort" unless the browser grants persistence:** the storage line says which. A browser
  under pressure may evict the files; eviction is reported and repaired by the next online visit. Saves in
  localStorage follow each browser's own eviction rules.
- **Background downloads need the page open:** the download runs in the service worker while a page is open;
  a browser may stop the worker if the tab is closed or backgrounded for long. It resumes on the next visit.
- **Chromium's offline emulation still attempts `sw.js` update checks.** The test server sees and drops them.
  Real offline devices simply fail them.
- **Only Chromium was tested** (desktop, headless, with H.264/AAC support). Firefox and WebKit weren't
  available here; codec support for the H.264 intro video on Linux Firefox builds without the codec is the
  video's own fallback path (`docs/AUDIO.md`), not an offline issue.
